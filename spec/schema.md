# 记录与控制规范

规则版本：2。数据格式：schema_version: 1。由 AGENTS.md 指定，不能扩大权限。

## 一、control 的格式与语义

`memory/control.md` 是唯一的持久开关来源。使用一个 YAML front matter 块，状态值采用带引号的字符串；正文只写简短字段说明，不记暂停原因或私人内容。

初次明确授权启用系统时的默认值：

```yaml
---
schema_version: 1
recording: "auto"
recall: "on"
local_commits: "on"
updated_at: "<实际写入时间>"
---
```

以上时间是模板占位符。实际文件必须使用真实可得时间，不得原样保存。升级或再次执行初始化时保留现有有效开关，不得把 paused/off 重置为默认值。

| 字段 | 允许值 | 精确定义 |
| --- | --- | --- |
| `recording` | `auto` / `paused` | 是否允许从正常对话自动提取并新增、补充个人内容 |
| `recall` | `on` / `off` | 是否允许为了回答当前问题主动检索、使用已有个人记忆 |
| `local_commits` | `on` / `off` | 是否允许在其他提交条件满足时自动创建本地 Git 提交 |
| `updated_at` | ISO 8601 日期或带时区时间 | 开关实际发生变更的时间；纯读取不更新 |

三者互相独立。例如 `recording=auto, recall=off` 表示可以记录之后的新内容，但不使用旧个人记忆个性化回答。为防重复、冲突而确需读旧内容时，只检查该条候选对应的最小范围，不能借写入流程读取整个画像。

`paused` 禁止自动新增、补充、重述个人内容以及保留“恢复后再记”的队列；允许执行用户明确要求的控制、单条保存、纠正、删除和必要的配套索引修改。这些是指定操作的授权，不改变暂停状态。

`recall=off` 不妨碍处理用户本轮新提供的信息；也不意味着技术上从已发送给模型的上下文中删除了历史内容。应停止主动使用旧个人事实，不能承诺撤回已传输的数据。

“这件事别记”默认限制当前指代内容本次进入持久存储。如果用户还要求之后都不记录某类信息，只保存不含具体敏感内容的最小排除偏好；如果连类别也不得保存，则只在当前可见上下文中遵守，并说明无法持久记住该限制。已有内容需要删除时按“忘记”处理。

关闭记录后没有后台清理或自动归档；需要时可以执行用户明确要求的维护。跨客户端或跨设备同步若改变 control，以用户明确的新指令为准；仅发现状态冲突时采用不自动记录、不主动调用的临时行为，不猜测哪一份开关更新。

## 二、记录格式、来源与更新协议

### 2.1 文件与记录

个人记录文件顶部使用 `schema_version: 1` 的 YAML front matter。每条记录以 `## m-<UUID>` 作为稳定标题和 ID，下一块为 YAML 数据。UUID 生成后保持不变，不用全仓计数器编号，也不把姓名等私密内容编码进 ID。

一条记录表达一个可以独立纠正的意思。不要把“身份、偏好、计划和能力”挤成一条，也不要把一句完整偏好拆成没有意义的碎片。

| 必需字段 | 含义 |
| --- | --- |
| `kind` | `fact` / `preference` / `goal` / `state` / `understanding` / `hypothesis` / `decision` |
| `content` | 忠于依据的简短表述，保留必要条件、否定和范围 |
| `scope` | 明确主体、场景或项目；未明确全局适用时不得擅自设为全局 |
| `status` | `active` / `tentative` / `disputed` / `superseded` / `expired` |
| `sources` | 非空来源数组，每项含 `type`、`basis`，定位和限制按下表补充 |
| `recorded_at` | 首次在本系统记录的实际时间，不等于事件时间 |
| `updated_at` | 内容、来源、适用范围或状态最后实际改变的时间 |

| 按需字段 | 何时使用 |
| --- | --- |
| `valid_from`、`valid_until` | 已知事件或事实的适用起止；不明时省略或为 null |
| `review_after` | 在特定日期后使用前需复核；只在依据或具体用途支持时设置，不统一编造有效期 |
| `related_ids` | 相关记录 ID，例如推断的依据、相互冲突的记录 |
| `supersedes` | 新记录实质替代并保留了哪条旧记录；填写旧 ID |

记录中的日期只精确到实际已知的程度。只能确定日期时用日期；知道时区和时间才写带偏移量的时间。转述材料里的事件时间不能冒充本次记录时间。

### 2.2 来源语义

| 来源 `type` | 允许表达的结论 |
| --- | --- |
| `user_statement` | 用户直接说了什么；并非已完成外部真实性核验 |
| `user_confirmation` | 用户明确确认了哪一项具体表述；确认不能扩展到没有确认的内容 |
| `artifact` | 实际读取的材料支持什么；材料内容不自动等于用户本人经历 |
| `inference` | AI 基于哪些独立依据提出什么暂定判断；不能只以另一段 AI 总结作证 |

每项来源的 `basis` 是必要短句或忠实摘要。`locator` 仅填写真实存在的可访问链接、文件位置或消息定位；没有则为 null，并在 `limitation` 中写明“仅依据本轮用户陈述，无持久消息定位”等实际限制。

引用本仓库记录时填写具体 ID。仅有间接历史摘要时保留其原有来源属性和限制，不能升级为用户本次确认。需要知道材料里“我”指谁而无法确定时，不建立用户事实。

通常把简短依据放进记录即可。仅当多个记录需要共享证据或确需独立核查时，才创建 `evidence/` 文件；不复制聊天流水账，不因追溯需求保留用户禁止保存的内容。

### 2.3 状态、纠正与时效

| 状态 | 使用方式与转变条件 |
| --- | --- |
| `active` | 当前可以在来源和范围限制内使用；不表示外部核验或永远有效 |
| `tentative` | 有依据但未确认；只能条件化参考，不据此下确定结论或扩大操作权限 |
| `disputed` | 相同主体、范围和适用时间存在未解决的冲突；先说明不确定性或核实 |
| `superseded` | 已被更正或取代，保留仅供历史查询；不能继续作为现状 |
| `expired` | 已知适用期结束或用户明确说明不再有效；不能继续作为现状 |

新增推断必须为 tentative。推断被复述多次、由不同 AI 重写、被收入 INDEX，都不能变为 active；必须出现新的直接确认或足以支持该具体结论的独立证据，并更新 sources。若已得到确认，将记录移到合适的权威分类并保留 ID 和来源演变依据。

纠正时先判断是“以前记错了”“情况后来改变了”还是“这次有特殊要求”。前两者更新对应记录，最后一种默认仅作用于当前范围。不能将所有新说法都当作全局偏好覆盖。

同一意思的修辞、补充来源和细化条件保留 ID。实质相反或替换的旧值若值得保存，则创建新 ID，用 supersedes 关联旧记录，旧记录标为 superseded；没有历史价值时直接修正原记录，不为错误内容制造永久备份。移动到 archive 不改变 ID，也不在原位置留一份相同正文。

超过 valid_until 的记录即使尚未写成 expired，读取时也不作为当前事实。超过 review_after 仅表示使用前需复核，不表示事实必然错误。暂停期间可在回答中遵守这些语义，无需为了改状态偷偷写记忆。

理解进展应具体到知识点和可观察证据，例如用户自己的解释、应用或明确反馈。记录尚存的疑问，不用“已讲解”代替“已掌握”，不设置没有校准依据的能力分数。

### 2.4 一次有效更新的边界

1. 确认用户当前任务和控制要求；无保存候选时结束记忆流程。
2. 重新读取 control、相关权威记录和必要 schema，比较主体、范围、时间、来源与隐私限制。
3. 确定最小修改集合，读取文件最新内容和 Git 状态；保存前确认没有意外变化。
4. 更新权威记录及必要证据，再修正受影响的链接和摘要；本轮新建文件不能覆盖已有同名文件。
5. 重新读取改动结果，检查字段、唯一 ID、状态、链接、敏感内容及差异范围。
6. 符合 Git 条件时提交；否则保留有效修改，明确区分“文件已保存”和“提交未完成”。

多文件修改不是天然原子事务。途中失败时，仅修复本轮能确认归属的修改；能安全恢复到本轮写前状态才恢复，不能覆盖其他人的后续改动。无法恢复一致性时停止自动提交及相关记录的使用，说明受影响的范围；不能自动重置仓库。

同样输入和证据再次出现而没有新增含义时，不新增重复记录、不更新日期、不制造提交。只有新的独立依据改变了结论、状态或实际可用性，才补充 sources。

### 2.5 虚构格式样例

以下仅用于 schema 和验收说明，不得复制进真实 memory。日期和人物意图都是测试设定。

````markdown
---
schema_version: 1
---

## m-11111111-1111-4111-8111-111111111111

```yaml
kind: preference
content: "代码审查时，先列出风险，再给修改建议。"
scope: "测试用户；代码审查场景"
status: active
sources:
  - type: user_statement
    basis: "虚构输入：以后帮我审查代码，都先说风险再说怎么改。"
    locator: null
    limitation: "虚构验收样例，不对应真实用户或对话。"
recorded_at: "2026-01-01"
updated_at: "2026-01-01"
```
````


## 三、检查器支持的书写格式

为跨客户端一致维护且不引入 YAML 依赖，正式文件使用以下 YAML 子集：

- control 和记录文件的 front matter 使用顶层 `key: value`，以独立 `---` 行包围。
- 记录标题独占一行 `## m-<小写 UUID>`，后接一个 `yaml` 代码块；记录内容写在该块内。
- `content`、`scope`、来源摘要、定位、限制和时间使用 JSON 兼容的双引号字符串；特殊字符按 JSON 转义。不要使用 YAML 块文本、锚点或自定义标签。
- 枚举可写为裸词或双引号字符串；版本写为整数。未知的可选值省略或使用 null。
- `sources:` 后使用两格缩进的 `- type: ...` 开始每项，该来源的其他字段使用四格缩进。
- 来源只使用 `type`、`basis`、`locator`、`limitation`；没有有效定位时 locator 为 null，并提供 limitation。
- `related_ids` 使用行内 JSON 字符串数组，`supersedes` 使用一个 ID 字符串。未知字段必须先更新协议，不能悄悄扩展。
- 每条记录必须有非空 sources。ID 引用在整个 memory 内唯一可解析；迁移到 archive 后更新文件链接。
- `memory/evidence/` 的独立来源摘要只要求版本 front matter，正文可用普通 Markdown，不强行改写成用户事实记录；通过具体文件定位引用。

检查命令为 `python scripts/check.py`。检查器只验证结构，不证明来源真实、内容低敏或模型行为正确；提交前仍需人工或 AI 核对本轮差异。
